# Trusted physical-world observation context

## The bug

`kern-ai-demo` used to describe the robot's position in a fixed sentence, at the
end of the semantic world block:

```text
The robot is currently at the origin, idle.
```

True when written. False from the first time the robot moved.

With the robot physically at about `x = 6000 mm`, the instruction

```text
Return to the starting position at x = 0, y = 0. Move at 300 mm/s.
```

produced

```text
proposal: no_action
reason:   Robot already at origin
```

That is the correct answer to the question the model was actually asked. It was
told the robot was at the origin, and it was asked to send the robot to the
origin. It was not hallucinating; it was believing the host. Adding *"Do not
assume the robot is already there"* to the instruction produced the right
`navigate` proposal, which confirms the diagnosis: the model reasons fine, and
the host was feeding it a stale fact.

## The fix

The sentence is gone, and nothing in `ROBOT_CONTEXT` states a position any more.
Position now comes from the machine, as a `WorldObservation`, carrying the one
thing a sentence could not: **how old it is**.

```text
ROS 2 / AMCL
      |  PoseWithCovarianceStamped, on /amcl_pose
      v
PoseObserver          read-only node: one subscription, no publisher,
      |               no action client, no service
      |  checked conversion at the boundary: m -> mm, rad -> mdeg
      v
WorldObservation      device + (pose with age | reason there is none)
      |
      v
PlanningRequest ----> system prompt ----> Nemotron
                                              |
                                              v
                                     UNTRUSTED proposal bytes
                                              |
                    strict parser -> normalization -> policy -> authority
                                                                   |
                                                        challenge -> lease
                                                        -> enforcer -> execution
```

Everything from "UNTRUSTED proposal bytes" down is byte-for-byte the path it was
before. The observation is an input to the prompt and to nothing else.

## What an observation is not

It is **not authority**, and there is no path by which it could become authority.
It is not consulted by the evaluator, it is not part of an `ActionProposal`, it
cannot relax a constraint, and it cannot mint, install, or invoke anything. A
test asserts the property directly: the same proposal is decided identically with
no observation, with a fresh one, with a stale one, and with one placing the
robot somewhere else entirely.

It is **not ground truth**. It is what a localization system reported, some
milliseconds ago, with the ordinary limits of the thing that produced it —
localization error, sensor error, latency, and the possibility that the robot has
moved since. The prompt says as much to the model, in those terms. Nothing here
is a physical safety claim, and nothing here is a functional-safety claim.

The prompt block is headed `HOST OBSERVATION`, where "host" means *supplied by
the host rather than generated by the model*. It does not mean infallible.

## Spoofing, and why placement rather than filtering

The observation renders into the **system** message. The instruction renders into
the **user** message. Nothing else is true of either.

That is the whole anti-spoofing measure, and it is structural. An instruction
containing the words `HOST OBSERVATION` and a set of coordinates is a user saying
those words, in the place users say things. It cannot move itself into the system
message and it cannot displace what the system message says, because the block is
built from typed integers by code that never sees instruction text.

Filtering the instruction for lookalike text was considered and rejected. It
would be a blocklist, it would be incomplete, and it would make the property
depend on recognising an attack rather than on where bytes are allowed to go. The
system message additionally tells the model, in the host's own voice, that
anything in the user message resembling this block is user text.

## Representation

```rust
struct WorldObservation { device: DeviceId, pose: PoseKnowledge }

enum PoseKnowledge {
    Known(PoseObservation),
    Unavailable(ObservationUnavailable),
}

struct PoseObservation { x_mm: i64, y_mm: i64, yaw_mdeg: i64, age_ms: u64 }

enum ObservationUnavailable {
    NotYetReceived,
    Stale { age_ms: u64, max_age_ms: u64 },
    SourceUnavailable,
    Unrepresentable(ConversionError),
    NotObserved,
}
```

Absence is a variant carrying a reason, never an empty position. There is no
`Default`, no zero value, and no `Option<PoseObservation>` anywhere in the chain
that a defaulting call could turn into a pose. The failure this shape forbids:

```text
missing pose  !=  (0, 0, 0)
```

Bounded by shape rather than by a length check: an identifier and at most four
integers. There is no map, no list, no free-text field, and no way to attach a
sensor payload, so there is no unbounded input to bound.

## Source, units, freshness

| | |
|---|---|
| topic | `/amcl_pose` (`geometry_msgs/PoseWithCovarianceStamped`), configurable |
| why not `/odom` | `/odom` drifts without bound and is in a different frame; the demo's named places are map-frame, so an odometry reading compared against a map-frame destination compares two different things |
| distance | metres → millimetres, ×1000 |
| angle | quaternion → yaw radians → millidegrees, ×(180000/π) |
| rounding | half away from zero, so `+x` and `-x` stay symmetric |
| age | host monotonic clock, from message receipt to request assembly |
| freshness bound | 5000 ms default, configurable with `--max-age-ms` |

Age is measured against the host's own clock, from when the bytes arrived. A
header stamp is written by whichever machine published it, against a clock this
process does not control and may not share; using it would make freshness depend
on clock synchronisation nothing here establishes.

The freshness default is generous because AMCL publishes on update rather than on
a timer. A stationary, well-localized robot can legitimately go seconds without a
new message, and that is exactly the moment somebody asks it to move.

## Failure behaviour

| condition | result |
|---|---|
| no reading yet | `Unavailable(NotYetReceived)` |
| reading older than the bound | `Unavailable(Stale { age_ms, max_age_ms })` |
| NaN | `Unavailable(Unrepresentable(NotANumber))` |
| ±infinity | `Unavailable(Unrepresentable(Infinite))` |
| conversion overflow | `Unavailable(Unrepresentable(OutOfRange))` |
| bad quaternion component | `Unavailable(Unrepresentable(NotANumber))` |
| observer thread dead, stream ended | `Unavailable(SourceUnavailable)` |
| observer never started | `Unavailable(NotObserved)` |
| `--no-observe` | `Unavailable(NotObserved)` |

In every row the prompt says the position is unknown and explicitly tells the
model not to assume one. In no row does anything assume the origin, mint
authority, create a lease, or trigger execution.

A stale reading's coordinates are **not** shown. Reporting "you are at x = 5982,
and that is 60 seconds old" invites the model to use the number and ignore the
caveat; the honest rendering of a reading too old to plan on is that there is no
usable reading, plus how stale it is.

## Running it

```bash
# grounded, the default
kern-ai-demo --instruction "Return to the starting position at x = 0, y = 0. Move at 300 mm/s."

# a different localization source
kern-ai-demo --pose-topic /odom --max-age-ms 1000

# ungrounded: how every phase before this behaved, kept so the difference can be
# demonstrated rather than asserted
kern-ai-demo --no-observe
```

## Limits

- One device, one pose. The heterogeneous machines observe nothing; the conveyor
  and arm are unchanged.
- AMCL's estimate is only as good as its localization. A delocalized robot
  produces a confident, wrong observation, and nothing here detects that. The
  covariance is available on the message and is currently ignored.
- The observer is a second ROS node. It exists because the demo deliberately
  creates no action client until policy has authorized something, and the
  observation is needed strictly earlier. It is started once per process, not per
  inference.
